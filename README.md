# PDSF: Prediction-Anchored Decomposition into Functional Subspaces

Code and prompt sets for:

**"Geometric and Behavioral Stratification in Transformer Residual Streams"**
Nelson Guda, 2026

## Overview

PDSF decomposes the residual stream of transformer language models into four strictly orthogonal subspaces ordered by proximity to the model's own prediction direction:

- **P (Predictive)** — rank-1 projection onto the unembedding vector for the model's predicted next token.
- **D (Discriminative)** — top-k PCA of the P-residual across prompts. Captures the high-variance content most related to prediction. Typically 4–12 dimensions.
- **S (Situational)** — top-k PCA of the double residual after removing P and D. Captures slower-varying contextual structure. Typically 10–16 dimensions.
- **F (Framework / the complement)** — everything that remains. Spans thousands of dimensions (>99% of the residual stream).

The decomposition guarantees `h = h_P + h_D + h_S + h_F` with strict orthogonality and lossless reconstruction at every layer.

The paper uses this coordinate system to measure a set of geometric and causal properties that are consistent across 18 models from 6 architecture families (7B–120B parameters):
prediction-proximal dimensionality does not scale with model width; a monotonic manifold complexity gradient is anchored to prediction proximity; the prediction-distal complement anti-discriminates, carrying prompt-specific configuration whose direction matters far more than its magnitude; and the two prediction-proximate subspaces produce dissociable behavioral effects when disrupted.

### A note on `data/`

Most of the paper's numbers are deterministic output of the notebook — clone, run, and you get them, which is why they are not duplicated in the repository. Three things do not work that way, and those are what `data/` contains: the behavioral classifications (a supervised judgment, not a computation), the generation pairs those classifications refer to, and 400 KB of Part G extracts standing in for 1.6 GB of source files that exceed GitHub's limits. Total ≈ 15 MB. See `data/README.md`, and the README in each subdirectory, for what reproduces which table.

### A note on `supplement/`

The paper's per-model metric tables and three extra intervention examples were moved out of the appendices to keep the reading copy compact. They are in `supplement/Paper_1_supplementary_materials.pdf`, which the manuscript cites by name (Tables B.5-2, B.6-2, B.7-1b, B.7-2, B.7-3, B.7-4, C.3, S1, and §S6). Every table in it recomputes from `data/` — each section names its source file.

## Quick Start

### Requirements

- Python 3.10+
- PyTorch 2.0+ with **CUDA**. The notebook checks for CUDA and stops if it is absent — Apple Silicon / MPS and CPU-only machines will not run it.
- GPU with ≥8 GB VRAM (test mode), ≥16 GB (7B models), ≥80 GB or multi-GPU (70B+ models)
- HuggingFace account with access to gated models (Llama, Gemma)

### Installation

```bash
git clone https://github.com/nelsonguda/pdsf-residual-geometry.git
cd pdsf-residual-geometry
pip install torch transformers accelerate bitsandbytes tqdm scipy matplotlib huggingface_hub
jupyter lab pdsf_pipeline_github.ipynb
```

Start Jupyter **from the repository root**. `BASE_DIR` defaults to `Path(".")`, so the prompt files under `prompts/` are located relative to the working directory. If you run the notebook from somewhere else — a pod that unpacks the repo under `/workspace`, for instance — set `BASE_DIR` to that absolute path in the configuration cell.

Model weights, temp files and offload go to a scratch root, **not** into the repository. The first cell uses `/workspace` when that is writable (the usual pod layout) and falls back to `./.pdsf_scratch` otherwise. Set the `PDSF_SCRATCH` environment variable to put the weights on a specific volume — worth doing deliberately, since a full run pulls roughly 400 GB.

### Test mode — this is the shipped default

The notebook ships with **`TEST_MODE = True`**. Running all cells as distributed performs a complete end-to-end verification run on `gemma-2-2b-it` (~5 GB) and writes real (reduced) output files. Test mode automatically:

- selects `gemma_2b`, the smallest model in the registry;
- keeps 3 whole SpecA groups for the geometry battery (48 prompts), cuts the Part G scramble sets to 4 prompts each, and shortens generation to 16 tokens;
- runs the geometry battery (Parts A–N) plus the single-pass Part G interventions on SpecA only;
- disables the transplant conditions, the spirality intervention phase, the Diverse continuation set, and the four F-dynamics conditions.

A reference run took **14.9 minutes** end to end on one H100 80GB (see the environment table below). Use it to confirm the environment works before committing to a full run.

Setting **`TEST_MODE_INCLUDE_FDYNAMICS = True`** alongside it keeps the small model and short generations but additionally enables the four F-dynamics conditions and the Diverse continuation set, so the step-offset injection path is exercised too. That costs roughly 15–25 minutes more.

### Full experimental run

1. In the **Model Selection** cell: set `TEST_MODE = False`, and edit `MODELS_TO_RUN` to select your model(s).
2. Run all cells.

**The shipped configuration reproduces the paper.** All three geometry prompt sets are enabled because Figure 3 has three panels; both F-intervention depths are enabled because about 12% is Figure 7 in the main text and about 70% is its depth control in Appendix B.5; and `RUN_PRESET = "all"` enables the four F-dynamics conditions behind Figures 8 and 9 and Table 5. The one deliberate exception is regime-level Diverse geometry, a stratified diagnostic Paper 1 does not report. You should not need to turn anything on to reproduce a reported result — only `MODELS_TO_RUN`, since the paper's testbed is 18 models and the default is one.

At the start of each model the notebook prints a **"WHAT WILL RUN"** summary: every enabled measurement with the section, figure or table it feeds, plus a clearly-labelled group for the things that run but are *not* reported in Paper 1 (the Part G transplant conditions, F-transplant, Part M spirality, and the Part E / Part H diagnostics). Check that block before committing to a long run.

A full run on a single 7B model (all geometry + continuation experiments) takes approximately 2–4 hours on an A100-80GB. A full 10-model run downloads roughly 400 GB of weights.

## What runs, and what you have to switch on

`RUN_PRESET` is the master switch and is applied at the end of Section 1 of the configuration cell, overriding the individual toggles above it:

| `RUN_PRESET` | Geometry (Parts A–N) | Part G interventions | Continuation | F-dynamics conditions |
|---|---|---|---|---|
| `"all"` (default) | yes | yes | yes | yes |
| `"geometry"` | yes | no | no | no |
| `"behavioral"` | no | yes | yes | yes |
| `"custom"` | as hand-set | as hand-set | as hand-set | as hand-set |

`TEST_MODE` is separate and takes precedence over all of it. Setting `TEST_MODE_FDYNAMICS_ONLY = True` alongside `TEST_MODE_INCLUDE_FDYNAMICS = True` narrows the smoke test to the F-dynamics path alone — no geometry, no Part G, no D/S/random/F-attenuate/F-mix/F-transplant — for a fast check of just those four conditions.

The **F-dynamics conditions** are the four persistent-hook experiments behind Figures 8 and 9 and Table 5. Each adds a full generation pass over its prompt set, so they are the most expensive switches in the notebook, and each is run on the prompt set the paper reports it on:

| Switch | Condition | Paper | Prompt set |
|---|---|---|---|
| `RUN_F_TOPK_ROTATION` | F-topK rotation | §6.4, Figure 8 | SpecB |
| `RUN_F_DYNAMIC_ROTATION` | F-dynamic rotation | §7.3, Figure 9 | SpecB |
| `RUN_STEP_OFFSET_INJECTION` | step-offset (stale-F) injection | §7.2, Table 5 | Diverse |
| `RUN_PASSIVE_F_TRACKING` | passive F tracking | §7.1 | SpecB + Diverse |

## Prompt Sets

**SpecA** (224 prompts): 14 groups × 16 variants in a 2⁴ factorial design crossing
paraphrase, constraint emphasis, preamble, and output format. Each group poses a
factual or logical question with a known single-token answer. Used for geometry experiments.

**SpecB** (96 prompts): 12 groups × 8 variants. Open-ended narrative starters that the
model continues for 64 tokens. Used for continuation/intervention experiments. The file
defines three tiers; `SPECB2_TIER` selects which is used, and the paper's continuation
results use the default `"standard"` tier — groups 01–10, **80 prompts**. SpecB *geometry*
(Part J / Part L, Figure 3 panel B) uses all 96.

**Diverse** (84 prompts): 21 groups × 4 variants spanning 8 linguistic regimes — code
completion, East Asian languages, English analytical, English narrative, formal mathematics,
Romance languages, structured instructions, and unusual register.

## Module Guide

### pds_continuation.py
The canonical implementation of the PDSF decomposition. Contains:
- `compute_P_bases_from_predictions()` — P basis from unembedding vectors
- `compute_D_basis_global()` — D basis via PCA of P-residual with adaptive rank
- `compute_S_basis_global()` — S basis via PCA of P+D residual with adaptive rank
- `decompose_hidden_state()` — Full P→D→S→F sequential projection
- `generate_with_D_scramble()`, `generate_with_S_scramble()` — Persistent rotational interventions
- `run_F_mix_experiment()`, `run_F_transplant_experiment()` — F intervention protocols
- `compute_F_topK_basis()`, `compute_F_dynamic_temporal_basis()` — the two F sub-bases (§6.4, §7.3)
- `run_F_subspace_rotation_experiment()` — persistent rotation within either of those sub-bases; the `run_F_topK_rotation` / `run_F_dynamic_rotation` names that appear in the config dict are option keys, not functions
- `run_step_offset_F_injection()`, `run_passive_F_tracking()` — the static/dynamic partition of F (§7)

### pds_geometry.py
Infrastructure layer. Contains:
- `MODEL_REGISTRY` — Maps short names to HuggingFace model IDs
- `load_model_bundle_multigpu()` — Multi-GPU sharding for models too large for one device (4-bit optional, and off under the default `PRECISION_OVERRIDE="bf16"`)
- `extract_hidden_states()` — Residual stream extraction at every layer
- `run_scramble_experiment()` — Part G geometry-level interventions
- `run_invariance_control()` — Null experiment (decompose-recompose identity check)

### specA_analysis.py
Geometry analysis pipeline. Implements Parts A–N of the SpecA experiment:
effective dimensionality (participation ratio), the six-estimator scaling-rank suite,
family separation, factorial effects, trajectory analysis, energy landscape, rotation
analysis, and injectivity.

### pds_spirality.py
Measures helical structure in residual stream trajectories: spectral concentration,
phase linearity (R²), and winding number. Diagnostic here; developed in the companion paper.

### pds_prompt_analysis.py
Optional. Quantifies the prediction-sharpness difference between SpecA and SpecB prompts.
No result from this module is reported in the paper.

## Model Precision and Reproducibility

Different architectures require different numerical precision, and precision affects the reproducibility of some results. The `PRECISION_OVERRIDE` setting (configuration cell, Section 2) controls it:

| Value | Meaning |
|-------|---------|
| `"bf16"` (**default**) | Force bf16 (brain-float 16). An undersized GPU fails loudly on OOM. |
| `"auto"` | Load bf16 if it fits detected VRAM; otherwise silently 4-bit quantize. |
| `"fp16"` | Force fp16. **Dense models only** — see below. |
| `"4bit"` | Force 4-bit (bitsandbytes NF4). |

The default is `"bf16"` deliberately. Under `"auto"`, any model that does not fit in available VRAM is silently loaded in 4-bit — different hidden states, and results comparable neither to the published run nor across models.

**Per-architecture requirements:**

- **Dense models** (Llama, Gemma, Mistral, Qwen) run in bf16 or fp16. **The published data was not produced under a single dtype**, and the output files do not record one. The pipeline that generated it branched on the model: Gemma-2 was forced to **bf16** (a workaround for NaN hidden states under fp16), GPT-OSS loaded in its **native MXFP4**, and everything else — Llama 8B/70B, Mistral 7B, Qwen 14B/72B, Mixtral 8×7B — took the general branch, which set **fp16**. This notebook defaults to bf16 for all of them, so a fresh run will not be bitwise comparable to the published behavioral numbers (see the precision-sensitivity note below); the geometry reproduces regardless.
- **Mixture-of-Experts** (Mixtral, GPT-OSS) must run in **bf16**, not fp16: recent `transformers` routes the MoE experts through a grouped-GEMM kernel that is bf16-only, and fp16 raises `Expected mat_a to be BFloat16 matrix got Half`. Do not set `PRECISION_OVERRIDE="fp16"` for MoE models.
- **GPT-OSS (MXFP4)** is released in native MXFP4 4-bit and should run in **native MXFP4**, which requires the `kernels` package and a matching Triton. Without `kernels`, `transformers` dequantizes MXFP4 to bf16 (~2× the size); for GPT-OSS 120B (about 65 GB native, about 240 GB dequantized) that forces CPU offload, which **corrupts the prediction/routing path and produces wrong results**. Install the pinned range below.

**Precision sensitivity of results:**

- **Geometry is precision-robust.** Participation ratios (§4.1), P–PCA orthogonality angles (§4.2), and manifold-complexity curvature (§4.3) differ only in ~the third significant figure between fp16 and bf16 — negligible against the effect sizes. These sections reproduce across precisions.
- **The identity-hook exact-match rate is model-dependent, and that is expected.** Passive F-tracking applies an identity modification — it decomposes the hidden state to P+D+S+F and sums it straight back — but that round trip runs in float32 against a bf16/fp16 state, so it is not bitwise identical and greedy decoding flips a fraction of prompts. The reported exact-match rate spans 0–100% across models. The meaningful check that the hook is read-only is the step-offset **k=0** control, where no prompt diverges within the generation window.
- **Greedy generation is not bitwise reproducible run to run.** Even at fixed precision on the same GPU with the same seeds, a small number of continuations flip because GPU reductions are not deterministic: across two runs of the smoke test, F-attenuate differed on 1 of 80 prompts, F-mix on 2 of 80, F-transplant on 7 of 168. Aggregate rates absorb this — F-mix's summary statistics were identical across those two runs — but per-prompt outputs should not be expected to match exactly.
- **Behavioral / generation results are precision-sensitive.** Greedy decoding can flip the argmax on borderline tokens under a small perturbation, so first-divergence tokens and category rates for the persistent-intervention experiments (§§5–7: D/S-scramble, F-topK/F-dynamic rotation, step-offset) shift on roughly one-third of prompts between fp16 and bf16. The *aggregate patterns* (D-before-S ordering, the F ≫ D ≈ S ≫ P hierarchy, category enrichment) hold across precisions; the exact per-prompt and summary numbers do not.
- **F-mix draws a random permutation, and the draw is what varies.** F-mix destroys coordinate structure in F by permuting and sign-flipping its components, so any single run is one sample from a distribution — the reported quantity is the rate across prompts and models, not a particular output. Two runs of this smoke test gave identical-output rates of 2.5% and 7.5%, against 56% for F-attenuate; the across-model spread in the paper is wider than that, and the F-mix ≫ F-attenuate ordering is unaffected. One implementation note: in earlier runs the per-prompt seed came from Python's built-in `hash()`, which is randomized per process (PEP 456), so `SPECB2_SEED` did not in fact pin the draw. It now seeds from `zlib.crc32`, so a given seed reproduces a given draw — outputs from this version will not match earlier runs.
- **To reproduce the paper's dense-model behavioral numbers exactly**, set `PRECISION_OVERRIDE="fp16"` for the dense models. The MoE / GPT-OSS numbers were produced in bf16 / native-MXFP4 and reproduce under those precisions. The testbed is mixed-precision by architecture, so no single global setting reproduces every number — match precision to the model class.

## Disk

A full 10-model run downloads roughly 400 GB of weights. `load_model_for_pipeline` filters `snapshot_download` to the standard sharded safetensors; without that filter several repositories ship two or three complete copies of the same weights and the total exceeds 690 GB. Weights are cached under the `HF_HOME` set in the notebook's first cell and are **not** deleted between models — clear them manually if disk is tight. Per-model outputs are a few hundred KB.

## Output Format

All results are saved as standards-compliant JSON (RFC 8259) with standardized metadata headers. Undefined numeric values are written as `null`, never as a bare `NaN`, so the files parse in any language.
File naming convention: `{model_key}-{Experiment}-{PromptSet}-{part}.json`

Example: `llama_8b-Geometry-SpecA-part_g_v11_scramble.json`

Outputs land under `{BASE_DIR}/results/Geometry/{model_key}/` and `{BASE_DIR}/results/Continuation/{model_key}/`.

## Scope notes

- **Part G condition scope.** The Part G intervention battery computes 14 conditions; the paper reports the 8 non-transplant ones. The six transplant conditions are retained so that the published Part G artefact reproduces exactly, but no transplant result appears in the paper. A full run writes `...-part_g_v11_regime_transplant.json`; a reduced run that drops the transplant conditions writes `...-part_g_v11_scramble.json` instead, so the filename always matches the conditions the file contains.
- **Part J control bins.** The PCA control sizes its F bin as `r_F = max(0, min(50, (n_prompts - 1) - (p_rank + k_D + k_S)))` and computes both the control bin and a rank-matched PDSF F at that rank, so the two are equidimensional. A secondary common-rank pass (`bin_F_common31` / `residual_rank_common31`) is emitted as a cross-model robustness check, and `basis_ranks.pca_control_rule` records the rule used in every output file.
